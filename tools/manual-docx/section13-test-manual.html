Deployment and Environments

A step-by-step script for BRD Section 13. You copy a tenant into a sandbox, bundle several kinds of configuration and custom code into one package, prove that a package with a missing dependency is refused, deploy a complete one, read the deployment log, and roll deployments back. Everything happens in throwaway tenants; your working tenant is never deployed into.

Before you start

Signing in

Address
http://localhost:5173
Who
An administrator (Super User) of the tenant being tested

Ask your Salesdam contact for the sign-in details. Pages can take 10–30 seconds to fill because the database is remote. Deployments and sandboxes are Super User screens: Setup → Deployments and Setup → Custom Code. The Tenant switcher in the top bar decides which tenant you are looking at, and a new change set is built from that tenant.

What can travel in a package

  • Yes: objects, fields, validation rules (alone or inside their object), layouts, layout assignments, flows, approval processes, approver groups, duplicate rules, configuration values, custom code (active version only) and document (PDF) templates.
  • Checked for dependencies: objects, fields (used by layouts, layout assignments and validation rules), layouts, roles, approver groups, custom code, document templates and integrations (a flow's integration is found by name).
  • Not packaged: integration configurations themselves (they hold credentials), email and message templates, users and records. Flows are checked for the objects, fields (on Update/Create/Get/Delete Record steps) and sub-flows they use; other step types are not inspected.

Cautions

  • Use only throwaway tenants as targets. Deploying changes the target's live configuration.
  • Validate first. A deployment re-checks the same dependencies and refuses to start if anything is missing.
  • Rolling back a package puts each component back to its state before the deployment; it does not touch records.

Sandbox and package

BRD §13.1–§13.2 — copy a tenant's configuration without its data, and bundle components into a package.

  1. Sign in as an administrator. In the top bar open the Tenant switcher and choose the tenant you want to copy (for the acceptance run, My Company). Open Setup → Deployments.
  2. Under Clone Sandbox Tenant choose My Company in Source tenant…, type S13 Sandbox A in Sandbox name and click Clone.
  3. Wait for the green message (it can take up to a minute on the remote database).
ExpectedThe message reads Sandbox created (N components). For My Company we saw 67 components: 5 objects, 48 fields, 2 layouts, 1 flow, 3 approval processes and the 7 Policy validation rules (rules travel inside their object). The Apps (workspaces) are copied too, so the objects show in the sandbox's sidebar, but not their members. Counts were read from the database by the Salesdam team.
  1. In the top bar open the Tenant switcher and choose S13 Sandbox A. Open Policies, Insured Lives, Claims and Brokers from the sidebar.
  2. Switch back to My Company and open Policies for comparison.
ExpectedThe Policies list reads 0 records and No policies found. (clicked). Insured Life, Claim and Broker lists were not clicked; their counts in the sandbox were 0 in the database (My Company held 8, 6, 8 and 0).
  1. Make something to package. In the S13 Sandbox A tenant add two text fields on Policy (S13 Reference, S13 Note, API names s13_ref, s13_note), one validation rule named S13 Note not BAD (s13_note == "BAD"), a Custom Code snippet s13_calc made active, a document template with API name s13_letter and a flow s13_flow that calls the snippet and generates that template. (The Salesdam team created these directly for the acceptance run.)
  2. With S13 Sandbox A selected in the top bar, open Setup → Deployments. Under Create Change Set type the name S13 Mixed Package.
  3. Add six components one at a time: choose the type, type the key, click Add: field policy.s13_ref; field policy.s13_note; validation_rule policy:S13 Note not BAD; custom_code s13_calc; pdf_template s13_letter; flow s13_flow. Click Create Change Set.
ExpectedThe six lines appear in the list and then the green message Change set created. The table under Change Sets shows S13 Mixed Package, status draft, 6 components. A wrong key (for example a typo in the field name) is refused with Components not found.
  1. With the source tenant selected in the top bar, find S13 Mixed Package in the Change Sets table and click Export.
ExpectedThe message Package file exported appears and a file named S13-Mixed-Package.salesdam-package.json downloads (about 5 KB). It holds format, version 1, the source tenant's name and id, the creation time, the six components with their settings, and a checksum. Anything that looks like a password, token, secret or API key is blanked; integration configurations are never included. The save dialog itself needs a person; we read the file's content from the page.

Package files

BRD §13.2 — export to a file, import into another tenant, refuse a tampered file.

  1. Switch the top-bar Tenant to the tenant that should receive the package (S13 Sandbox target). Under Import Package File choose the file you exported. Needs a person: the file chooser cannot be driven by our tool; we supplied the same file to the same screen handler instead.
  2. A new row S13 Mixed Package (draft, 6 components) appears in Change Sets. Choose a target tenant (a tenant without the object is blocked at Validate with Missing object: policy; S13 Sandbox Del, another clone, passes), click Validate then Deploy, and read the Deployment Log.
ExpectedImport message: Package imported as a change set. Validate and Deploy behave exactly as in the earlier tests: the log row reads deployed with 6 components, the By column names the administrator, and Rollback removes the components again (clicked end to end).
  1. In the receiving tenant, import a copy of the file in which you changed one setting (for example edit the snippet's description) without recalculating the checksum.
  2. Import copies in which: the version is 2; a component type is changed to user; the file is not JSON at all.
  3. Look at the Change Sets table after each attempt.
ExpectedEach is refused with a red message: Package refused: the integrity checksum does not match – the file was changed after export., package version 2 is not supported (expected 1), the same checksum message for the changed type, and the file is not valid JSON. No row is added (clicked). Also refused, proved by the automated suite only: an unknown component type or an operator key with a valid checksum, a component whose key does not match its settings, a file over 5 MB, and any import by a non-Super User.

Dependency checks

BRD §13.2 — a package is refused when something it needs is missing in the target.

  1. Under Target Tenant choose a tenant that has none of your objects (the acceptance run used an empty tenant, ZZ_S13 Bare Target). In the S13 Mixed Package row click Validate.
ExpectedValidation Result reads Blocked – 1 required dependency is missing in the target tenant and lists Missing object: policy. The Deploy button stays greyed out.
  1. Create a second change set, S13 Flow Only, containing only the flow s13_flow.
  2. Under Target Tenant choose the second sandbox (S13 Sandbox target, a clone of My Company, which has Policy but no snippet or template). Click Validate on S13 Flow Only.
ExpectedBlocked – 2 required dependencies are missing: Missing custom code: s13_calc (needed by flow:s13_flow) and Missing document template: s13_letter (needed by flow:s13_flow).
  1. Create a third change set, S13 Rule Only, containing only the validation_rule policy:S13 Note not BAD. With the same target selected click Validate.
ExpectedBlocked – 1 required dependency is missing: Missing field: policy.s13_note (needed by validation_rule:policy:S13 Note not BAD).
  1. Package a flow whose steps write a field, create records on an object, or call a sub-flow that the target does not have, and click Validate against that target.
ExpectedBlocked with Missing field: policy.<field>, Missing object: <object> or Missing flow: <sub-flow>. Putting the sub-flow in the same package clears its entry. Not clicked: proved by the automated suite. Fields are checked for Update Record, Create Record, Get Records and Delete Records steps; other step types are not inspected.
  1. Deploy is disabled in the screen until a package validates, so this step uses the API: with S13 Sandbox A selected, call POST /api/v1/change-sets/<id of S13 Flow Only>/deploy with the target tenant id. (The Salesdam team did this from the browser; it needs a person who can call the API.)
  2. Under Target Tenant choose S13 Sandbox target and read the Deployment Log at the bottom of the page.
ExpectedThe API answers 409 Deployment blocked: missing dependencies (s13_calc, s13_letter). The log gains a row, status blocked, 2 missing (hover the row to see which). Nothing was created in the target.

Deployment, log and rollback

BRD §13.1.2, §13.3 — deploy, read what happened, and undo it.

  1. Select S13 Sandbox target as the target and click Validate on S13 Mixed Package, then Deploy.
ExpectedAll dependencies are present – ready to deploy. The package status becomes deployed, 6 components, and a Rollback button appears. Switch to the target tenant and open Setup → Custom Code: s13_calc shows Active: v1 · 1 version with the note Deployed from change set (clicked). The fields, rule, template and flow were read from the database: both fields, the rule, the template, and the flow whose PDF step points at the target's own template, not the source's. Those Setup screens were not clicked.
  1. With S13 Sandbox target still chosen under Target Tenant, read the Deployment Log table.
ExpectedOne row per attempt with When (date and time), Change set, From (source tenant), By (the administrator's name), Status (deployed / blocked / rolled back) and Components. Blocked and rolled-back attempts stay in the log.
  1. In S13 Sandbox A make a second version of s13_calc active (Setup → Custom Code → Activate v2; the acceptance run set it directly).
  2. Create a change set S13 Code Update with the single component custom_code s13_calc. Choose S13 Sandbox target, click Validate, then Deploy.
ExpectedValidation passes and the log shows S13 Code Update – deployed – 1. In the target the snippet now has v2 active and v1 archived (read from the database). Only the active (approved) version is ever packaged, never a draft.
  1. In the Deployment Log of S13 Sandbox target, find the S13 Code Update row and click its Rollback button.
ExpectedThe row's status changes to rolled back and its Rollback button disappears. In the target the snippet is back to v1 active with only v1 present (the previous state, exactly).
  1. In the same log click Rollback on the S13 Mixed Package row.
ExpectedStatus becomes rolled back. The snippet is gone from the target's Custom Code page; in the database the target again had no s13_ fields, no rule, no template and no flow. A component that already existed before the deployment would instead be put back as it was.
  1. Open Setup → Custom Code in S13 Sandbox A. Find s13_calc (Active: v2 · 2 versions) and click View code.
  2. Click Restore v1 (the browser may ask you to confirm).
ExpectedThe heading changes to Active: v1 · 2 versions; v1 reads active, v2 archived. The previous version was kept all along, so nothing is lost.

Cases checked by the test suite only

BRD §13.1.3, §13.2.7 — not clickable on a standard screen.

  1. Create a snippet that has only a draft version, add it to a change set as a custom_code component and click Validate against any tenant.
ExpectedBlocked with Missing custom code approved version: <snippet name>. Not clicked: proved by the automated suite (section13-deployment).
  1. Package a flow whose HTTP step uses an Integration (external object) and validate it against a tenant without an integration of the same name.
ExpectedBlocked with Missing integration: <name>. Not clicked: proved by the automated suite. The integration itself is not packaged (it holds addresses and credentials); each tenant sets up its own and the package finds it by name.
  1. Under Delete Sandbox Tenant open Sandbox to delete…. Only tenants created with Clone are listed; a tenant that was not made by cloning (for example the empty target) and your real tenants are absent.
  2. Choose the sandbox you are currently working in: Delete sandbox… is greyed out and the note You are working in this sandbox. Switch to another tenant in the top bar first. appears.
  3. Switch to another tenant, choose a sandbox, click Delete sandbox…, type a wrong name (the Delete permanently button stays disabled), then type the exact name and click Delete permanently.
ExpectedThe message Sandbox deleted appears and the sandbox leaves both pickers (clicked). Its configuration, users, roles, change sets and logs are removed; the source tenant is untouched. The server also refuses (suite): a non-clone tenant, the tenant you are signed in to, a wrong name and a non-Super User.

Known limits

Worth knowing

  • A package file is JSON with a checksum; it is checked before anything is created, but it is not encrypted or signed, so treat it like any other company file.
  • A deployment does not carry users, records, email/message templates or the credentials of an integration.
  • Deploying a custom-code component adds it as the next version in the target and activates it; the target's earlier version stays in its history.
  • Sandbox cloning copies configuration, Apps and every custom-code version (drafts included), but no records, users, App members or files. The sandbox starts without members, so only Super Users see its Apps until you add people.
