What has already been set up for you

  • SA Provinces — a Global Value Set of all nine provinces, Gauteng marked as default.

  • Insurance — a workspace containing both objects.

Two things worth knowing before you begin

  • Pages take a while to open. This environment runs the application on your machine but keeps its database in the cloud, so every screen waits on a number of round trips. Ten to thirty seconds for a setup or record page is normal here and is not a fault in the feature you are testing. Give a page time before deciding it is stuck.
  • A new object is invisible until you add it to a workspace. After creating an object, go to Setup → Workspaces → Insurance → Objects, tick it and save. Otherwise you get "This object isn't available".

Part 1 — Object definition

BRD §3.1.1 – §3.1.3. You will create a throwaway object, inspect how the platform names it, check its settings, and look at the two relationship types.

  1. Go to Setup → Object Settings → New Object.
  2. In Object Label type Eye Glass.
  3. Watch the Plural Label and API Name boxes without touching them.
Expected Plural Label fills in as Eye Glasses and API Name as eye_glass — spaces become underscores. The API Name box stays editable.
  1. Still on the New Object form, clear API Name and type 2glasses, then try to save.
  2. Try eye__glass (two underscores), then eye_glass_ (trailing underscore).
  3. Finally set it back to eye_glass.
Expected Each invalid value is refused with a message explaining the rule. Names must start with a letter, contain only letters, numbers and underscores, and have no doubled or trailing underscores.
  1. On the New Object form for Eye Glass, scroll to Object Settings.
  2. Tick Enable Type Field, and untick Allow Search and Allow Notes.
  3. Add a Description, then click Create Object.
  4. When the object opens, look at Object Settings again.
Expected Every toggle is exactly as you left it on the create form — Enable Type Field on, Allow Search and Allow Notes off — without having to save a second time. Your Description is there too.
  1. On the Eye Glass object you just created, open the Fields tab.
  2. Find the field called Type.
  3. Open it and add the values Prescription and Sunglasses.
Expected A picklist named Type is already there, marked System and Protected, created the moment you ticked Enable Type Field. You can still add, rename and deactivate its values like any other picklist — no special tooling.
  1. On Eye Glass → Object Details, untick Allow Reports and save.
  2. Go to Analytics and try to build a report over Eye Glass.
  3. Switch Allow Reports back on and try again.
Expected With the toggle off, Eye Glass cannot be reported on — the platform refuses with a message saying reporting is turned off for that object, even though you can still read its records. Switching it back on restores reporting.
  1. Open Policy from Object Settings.
  2. Look at the Name Field Type panel.
Expected The system Name field reads "This field is locked and cannot be changed". Its label stays editable while its API name does not.
  1. Open Insured Life → Fields and click the pencil on the Policy field.
  2. Read the explanatory line under Parent Object.
Expected Type is Master Detail, parent is Policy, and the form states that records are owned by the parent and deleted with it. Only one Master-Detail field is allowed per object unless the object is marked as a Junction Object.
  1. On Eye Glass, add a new field of type Lookup.
  2. Pick a target object and inspect the deletion options.
Expected You can choose what happens to the child when the parent is deleted — block the deletion, clear the reference, or do nothing. Deleting a parent does not delete children by default, which is what separates a Lookup from a Master-Detail.
  1. Open Eye Glass and click Delete Object.
  2. Read the message before confirming.
Expected You are told exactly what will go with it — how many records and how many fields — and must confirm before anything is removed. Deletion never happens on a single unconfirmed click. Delete Eye Glass once you have read the message; the rest of the script does not need it.

Part 2 — Fields and data types

BRD §3.2.1 – §3.2.2. The Policy object already carries one field of nearly every supported type, so most of this is inspection rather than building.

  1. Open Policy → Fields → Add Field.
  2. Open the Type dropdown and read the whole list.
Expected All of these appear: Text, Text Area, Number, Currency, Percent, Date, Date/Time, Checkbox, Picklist, Multi-select, Rich Text, Time, Address, Email, Phone, URL, Auto Number, Lookup, Master Detail, Formula, Rollup Summary.
  1. In the Add Field dialog type Label = Policy Number.
Expected API Name fills in as policy_number and remains editable.
  1. Still in the Add Field dialog, find Field-Level Security.
  2. Note which option is selected before you touch anything.
  3. Open the list and read the three choices.
Expected It defaults to Hidden, so a newly created field is not exposed to anybody until an admin grants it. You can instead choose Read-Only or Visible, and whichever you pick is applied to every existing profile the moment the field is created. Cancel out of the dialog when you are done.
  1. Open Policy → Fields and note the help text on Policy Number.
  2. Now go to Policies in the left sidebar and click New.
Expected The same guidance — "Internal policy reference. Must be unique." — is shown to the user beside the field on the record form.
  1. On the New Policy form, clear Policy Number and Monthly Premium.
  2. Click Create Record.
Expected The save is refused and inline messages appear — "Policy Number is required" and "Monthly Premium is required". The record is not created.
  1. Create a new Policy with Policy Number = POL-TEST-001 (the value already used by the existing record) and Monthly Premium = 100.
  2. Save.
Expected The save is refused because Policy Number must be unique across Policy records.
  1. Create a valid new Policy — Policy Number POL-TEST-002, Monthly Premium 750, Start Date any date.
  2. Look at the Name shown on the saved record.
Expected The record is named POL-00002 — the configured prefix POL- with five-digit zero padding, one higher than the previous policy. The user never types it.

Part 3 — Picklists and value sets

BRD §3.2.3. Field-level lists, shared catalogues, deactivation and defaults.

  1. Open Policy → Fields and edit Policy Status.
  2. Type a new value into the Picklist Values box and press Enter.
  3. Add another using the Add button instead.
  4. Remove both again before closing.
Expected Four values belong to this field alone: Quoted, Active, Lapsed, Cancelled. Both Enter and the Add button add a value, and pressing Enter adds the value rather than submitting the whole field. You can add and remove values here without affecting any other field.
  1. Go to Setup → Global Value Sets and open SA Provinces.
  2. Add a tenth value, Test Province, and save.
  3. Now open Policy → Fields → Province.
Expected The Province field is linked to the set, and the new value appears there automatically — you never edited the field. Remove Test Province again afterwards.
  1. In SA Provinces, switch Limpopo to inactive using the Active toggle, and save.
  2. Create a new Policy and open the Province dropdown.
Expected Limpopo is no longer offered for new records, but any record that already holds it keeps the value and still displays it. Switch it back on when finished.
  1. Confirm Gauteng carries the ★ in SA Provinces, and that Policy Status has Active in its Default Value box.
  2. Open Policies → New and look at Policy Status and Province before typing anything.
  3. Fill in only the required fields and save.
Expected The form opens with Policy Status already showing Active and Province already showing Gauteng — one from the field's own default, the other from the value starred in the shared set. Both are saved on the record, and the user can change either before saving.

Part 4 — Formulas and roll-ups

BRD §3.2.4 – §3.2.5. Calculated fields and parent-level aggregates.

  1. Open Policy → Fields → Annual Premium.
  2. Change Return Type between Number, Text and Date, watching the Functions panel each time.
  3. Click the Fields tab in that panel, then Show more under Functions.
Expected The function list changes with the return type, offering only functions that can produce it. Available fields on Policy are listed and clicking one inserts it. IF, AND, OR, ISBLANK, TEXT, CONCATENATE, arithmetic and date functions are all present.
Where ISCHANGED lives ISCHANGED compares a value against what it was before the save, so it belongs to Validation Rules (Section 6) rather than formula fields — a formula is calculated from the record as it stands and has no earlier value to compare against. You will find it when you test validation rules.
  1. Open policy POL-00001 and note Monthly Premium (500) and Annual Premium (6,000).
  2. Edit the record, change Monthly Premium to 600, save.
Expected Annual Premium becomes 7,200 immediately. It is read-only throughout — it is calculated from monthly_premium * 12, never typed. Set it back to 500 afterwards.
  1. Open Policy → Fields → Total Insured Lives.
  2. Note the Summarised Object, Related Via and Aggregate settings.
  3. Open the Aggregate dropdown, then look at Filter Criteria below it.
Expected It summarises Insured Life via the Policy relationship. The aggregate list offers Count, Sum, Min, Max and Average, and an optional Filter Criteria box restricts which child records are counted. Only objects that are children of Policy can be summarised — a roll-up cannot be pointed at an unrelated object.
  1. Open POL-00001 and compare Total Sum Assured with Spouse Cover Total.
  2. Open Policy → Fields → Spouse Cover Total and read its Filter Criteria.
Expected Total Sum Assured is 450,000 — every life on the policy. Spouse Cover Total is 150,000, because its filter relationship == "Spouse" counts only Naledi. Both summarise the same child records; only the filter differs.
  1. Open POL-00001. Note Total Insured Lives (3) and Total Sum Assured (450,000).
  2. Scroll to the Insured Lives related list and click New.
  3. Add Name Kabelo Mokoena, ID Number 0803145566088, Relationship Child, Sum Assured 25000. Save.
  4. Reload the policy.
Expected Total Insured Lives becomes 4 and Total Sum Assured becomes 475,000, without any manual recalculation. Spouse Cover Total stays at 150,000, because the new life is a Child. Delete Kabelo and confirm the totals fall back to 3 and 450,000.
Where children are created An Insured Life belongs to a Policy, so it is created from the related list on a Policy — that is where the Policy field is filled in for you. This is the normal Master-Detail pattern and applies to any child object.

Part 5 — Duplicate detection

BRD §3.4. Matching rules and what happens when a match is found.

  1. Go to Setup → Duplicate Rules and open Insured Life — duplicate ID Number.
  2. Click Add field to add a second criterion.
  3. Open the When a duplicate is found dropdown.
Expected Any field on the object can be matched, each as exact or case-insensitive. Adding a second field reveals an all of these match / any of these match selector (AND / OR). The action list offers Warn, Block, Present matches, Use existing and Trigger flow. The form states the rule applies to forms, imports and the API.

Remove the extra criterion before continuing.
  1. Open POL-00001 and click New on the Insured Lives related list.
  2. Enter Name Duplicate Check, ID Number 8001015009087 — the ID already held by Thabo Mokoena — and Sum Assured 50000.
  3. Click Create.
Expected A Duplicate record found panel appears explaining that your duplicate rules do not allow saving it. It names the record you clashed with — Thabo Mokoena — says it Matches on ID Number, and gives you Open to go to that record or Back to form to correct yours. No new record is created.

Part 6 — Object and record lifecycle

BRD §3.1.2.3, §3.1.3. Deactivation, cascade ownership, the Recycle Bin, and many-to-many relationships.

  1. Open Insured Life → Object Details, untick Active and save.
  2. Look at the sidebar and at Setup → Object Settings.
  3. Tick Active again and save.
Expected While inactive the object disappears from navigation and from the active object list, and moves to the Inactive tab — but nothing is deleted. Reactivating brings it back with all three insured lives intact. This is the safe step to take before deleting an object.
  1. Create a throwaway policy — Policy Number POL-CASCADE, Monthly Premium 100, Start Date any date.
  2. From its Insured Lives related list, add two lives with any details.
  3. Delete the policy, then look for those two lives under Insured Lives.
Expected Both lives go with the policy — that is what Master-Detail ownership means. Neither is left behind pointing at a policy that no longer exists.
  1. The policy and lives you deleted in test 29 are in the Recycle Bin. Open Policies and look for the deleted-records view.
  2. Restore POL-CASCADE.
  3. Delete it again once you have seen it come back.
Expected Deleting does not destroy a record immediately — it goes to the Recycle Bin and can be restored. Records are kept there for a configurable window, 30 days by default, and are permanently removed only once that window passes.
  1. Create an object Plain Link and add a Master Detail field to Policy.
  2. Try to add a second Master Detail field, this time to Insured Life.
  3. Create a second object Junction Link, this time ticking Junction Object, and add Master Detail fields to both Policy and Insured Life.
  4. Delete both throwaway objects when done.
Expected The second Master-Detail on Plain Link is refused — one parent per object. Junction Link accepts both, which is how a many-to-many relationship is built: a small object in the middle owned by two parents.
  1. In Setup → Duplicate Rules, create a rule on Insured Life matching on Name and Date Of Birth, with all of these match and Block.
  2. Add a life with any name and a date of birth, then add a second with the same name but a different date of birth.
  3. Now add a third with the same name and the same date of birth.
  4. Delete the rule and the test lives when done.
Expected The second saves — only one of the two fields matched, and the rule needs both. The third is blocked and shows the clash. Switching the rule to any of these match would block the second as well.

Reporting a problem

For anything that does not match the expected result, note the test number, what you saw instead, and the record or object you were working on. A screenshot of the screen as it looked when it went wrong is usually enough for us to reproduce it.
