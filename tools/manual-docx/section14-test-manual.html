Tenant Configuration

A step-by-step script for BRD Section 14. You see which settings a company can change, override one and reset it, watch the platform default take over, set a company's name, colour and logos and see them appear (and fall back), and prove that saved credentials are masked, encrypted and kept out of logs. Everything that changes data happens in a throwaway copy of a tenant, which is deleted at the end.

Before you start

Signing in

Address
http://localhost:5173
Who
An administrator (Super User) of the tenant being tested

Ask your Salesdam contact for the sign-in details. Pages can take 10–30 seconds to fill because the database is remote. The Configuration page is under Setup → Admin Settings → Configuration. The top-bar Tenant switcher decides which tenant you are changing.

Prepare a throwaway tenant

  • Open Setup → Deployments, choose your working tenant under Clone Sandbox Tenant, name the copy S14 Config Sandbox and click Clone. Switch to it with the Tenant switcher.
  • Use dummy credentials only. Never type a real password, token or key into this script.

Cleaning up

  • Switch back to your working tenant, then delete the copy with Setup → Deployments → Delete sandbox… (type its name). This removes its settings, credentials, email senders and webhooks.
  • Remove any platform setting you created (tests 3–5) and return any value you changed in your working tenant with Reset.

Settings and the order they are read in

BRD §14.1–§14.3 — the company's value, then the platform's, then the built-in default.

  1. Sign in as an administrator. Open Setup → Admin Settings and click the Configuration card.
  2. Read the list. Each row shows the setting's name, its key, a description, the current value, and a badge.
ExpectedThe page lists about 34 settings (approval threshold, recycle-bin retention, default currency, minimum deal value, communication consent, branding, integration credentials, call-recording retention, file limits, password and login rules, MFA and single sign-on). A setting nobody has changed carries Platform default; one the company has changed carries Company value and a Reset button.
  1. On the Configuration page change Default Currency from ZAR to USD and click Save.
  2. Read the row, then click Reset on it.
ExpectedAfter Save the badge reads Company value and a Reset button appears. After Reset the badge returns to Platform default and the value to ZAR. (Clicked; the same check was repeated for the Approval Threshold Amount in Section 8 and the Minimum Deal Value in Section 6.)
  1. Needs an API call: as a Super User call PUT /api/v1/configuration/defaults/platform.default_currency with {"value":"EUR"}. The screen offers no editor for an existing default; its Add platform setting box creates new ones.
  2. Open the Configuration page in a tenant that has no override: the row shows EUR with the Platform default badge.
  3. Save USD as that company's value, then click Reset. Finally DELETE /api/v1/configuration/defaults/platform.default_currency.
ExpectedOrder of precedence seen at each step: ZAR (built-in default) → EUR (operator default) → USD (company value) → after Reset EUR → after deleting the operator default ZAR. The three levels are exactly: the company's own entry, then the platform entry, then the built-in value.
  1. As a Super User click Add platform setting. Type the key s14.demo_limit, label S14 Demo Limit, default value 7, and click Add for every company.
  2. Check the row appears. (Afterwards remove it: DELETE /api/v1/configuration/defaults/s14.demo_limit.)
ExpectedThe row S14 Demo Limit appears with the Platform default badge and the key. Validation rules can read it with CONFIG("s14.demo_limit"). The box is shown to Super Users only.
  1. Needs an API call to prepare: as a Super User create a platform setting with "editableByTenant": false (PUT /api/v1/configuration/defaults/s14.locked_setting).
  2. Open the Configuration page and find the row S14 Locked.
  3. Try to save a value for it through the API: PUT /api/v1/configuration/s14.locked_setting. Remove the setting afterwards.
ExpectedThe row is shown but its field and Save button are greyed out (clicked). The API answers 403 Configuration key 's14.locked_setting' is not available for tenant override. An unknown key is refused the same way.
  1. Needs a person: sign in as an ordinary company administrator (not a Super User) in a second browser window. Open Configuration: every setting is listed, an ordinary one (for example Recycle Bin Retention) can be saved and reset, the locked row from test 5 is greyed out, and there is no Add platform setting box.
  2. Then call PUT /api/v1/configuration/defaults/records.recycle_bin_retention_days from that window.
ExpectedThe platform-defaults call answers 403, as do the matching GET and DELETE. Proved by the suite section14-config (40/40), which creates a throwaway tenant with a real, non-Super-User administrator (random password, never printed), signs in over HTTP and checks: can view the list, can override and reset an editable key, cannot override a locked key (403), cannot read, change or delete operator defaults (403). The screen itself was not clicked as that person: the browser pane holds one signed-in user.
  1. Create a copy of your working tenant (Setup → Deployments → Clone Sandbox, Section 13). In the top bar Tenant switcher choose the copy, open Configuration, and set a company name, colour and logo (test 12).
  2. Switch back to your working tenant and open Configuration and look at the page header.
ExpectedThe working tenant still shows Salesdam, the default colour and no logo; its Branding rows say Platform default. The pre-sign-in branding address (test 14) returns the copy's branding for the copy and the default for the working tenant. The suites tenant-isolation (23/23) and section14-config prove the same for two tenants.
  1. No new steps: these were clicked in earlier sections. Validation rule CONFIG("deals.minimum_value") follows the Configuration page (Section 6, Test on CONFIG); an approval entry criterion reads the Approval Threshold Amount (Section 8); the recycle-bin purge reads its retention days per tenant (Section 3); flows read settings through the same CONFIG() function.
  2. Settings that are stored but not yet read by any behaviour are listed under Known limits.
ExpectedEach behaviour reads the company's own value first, then the platform value, then the built-in default. Single sign-on, password policy, lockout, MFA, file-size and file-type limits, default currency, call-recording retention, communication consent, the default communication template and the WhatsApp, Meta, telephony and webhook keys also read the company's value first (tests 9–11 and the credential tests near the end).
  1. On the Configuration page set Default Currency to EUR and click Save. Open Setup → Admin Settings → Company Information.
  2. Create a record on an object that has a Currency field (for example a Deal) and leave the field empty. Then click Reset on Default Currency.
ExpectedCompany Information reads Selected currency: Euro (EUR) (clicked; it read South African Rand before). The sign-in session carries EUR, so every amount the application formats uses it. A new record with an empty Currency field receives the tenant's code (suite; not clicked). The order is the company's value, then a platform-wide value (test 3), then the built-in ZAR; another company is unaffected. A company that only ever used the older Operating Currency box on Company Information keeps that choice until a Default Currency is set.
  1. Set Call Recording Retention (days) to 7 on a throwaway tenant. The built-in value is 0, which keeps recordings for ever.
  2. Needs a person with database access: add two call activities carrying a recording link, one 30 days old and one 1 day old, and a 400-day-old call in a second tenant that has no retention set. Wait for the hourly sweep (or run it from a script).
ExpectedOnly the 30-day-old call in the tenant with the 7-day window loses its recording link (a purge time is stamped; the call itself, who, when and how long, stays). The 1-day-old call and the other tenant's 400-day-old call are untouched. A value of 0 or a negative number purges nothing. Proved by the suite with throwaway data (the purge job mirrors the recycle-bin job: hourly, one tenant at a time, a failure in one tenant does not stop the rest). The Configuration row itself was saved by clicking, as in test 2.
  1. Set Enforce Communication Consent to Yes on a throwaway tenant. Record that a client has opted out of email (Section 17's consent screen), then queue an email to that client (a policy communication, an Inbox reply, a flow's send step or custom code).
ExpectedWith enforcement on the send is refused with Contact blocked: consent withdrawn; with enforcement off, the default, it goes ahead. Default Opt-In (unknown consent) decides what happens for clients with no record. The Inbox, flow and custom-code paths already checked consent; the queued policy communications did not and now do (suite).

Branding

BRD §14.4–§14.16 (tenant branding) — name, colour and logos per company, with a Salesdam fallback.

  1. In the throwaway tenant (see Before you start) open Configuration. In the Company Name row type Acme S14 and click Save.
  2. In Primary Brand Colour type #B8312F (a colour picker appears beside the box once the value is a valid colour) and click Save.
  3. In Company Logo URL and Login Page Logo URL use the file button to choose a small PNG (up to 500 KB; a preview appears) or paste an https address, then click Save on each row. Needs a person: the operating-system file chooser cannot be driven here; the acceptance run supplied the file to the same handler.
ExpectedEach row turns to Company value and a green message names the setting. No developer, deployment or restart was needed.
  1. Reload the page and look at the top bar and the user avatar. Then open Audit Logs from the sidebar and look again.
  2. Click a different workspace in the sidebar and look again (not clicked in the acceptance run).
ExpectedThe top bar shows the company logo (our test image, 64 px square shown at 24 px) and the avatar and accents take the company colour (#B8312F). Seen on the Configuration and Audit Logs screens (clicked). The bar is part of the shared page frame, so every workspace and standard screen uses it. The company name is shown in place of the logo when no logo is set.
  1. Open the public branding address, with no sign-in: GET /api/v1/configuration/public-branding?tenant=<tenant id or slug>.
  2. Open the login page without signing out of the administrator window: use a second browser or a private window, or the same machine under the other host name (http://127.0.0.1:5173/login?tenant=<tenant id> when you normally use localhost), so no sign-in cookie applies. A browser that has signed in to the tenant before shows the same branding without the ?tenant= part.
ExpectedThe address answers with only the four branding values (company name, colour, logo, login logo): Acme S14, #B8312F and the images for the copy; Salesdam, #0066FF and no logo for the default. Nothing else is exposed, no key marked secret is ever returned, and the address is rate limited (120 a minute per visitor). Before this change the login page asked for the authenticated settings list, so it could only ever show Salesdam. Clicked (second host name): the login screen for the copy read Acme S14b in place of Salesdam and its Sign in button took the company colour (rgb(5, 5, 15)); with no tenant given the same screen read Salesdam in the default colour (#244C64). The header logo is read from the same value; a login-page logo image was not seen on screen in this run.
  1. In the throwaway tenant click Reset on each of the four Branding rows.
  2. Reload and look at the top bar and the public branding address from test 14.
ExpectedThe rows return to Platform default, the top bar shows Salesdam with no logo and the default blue (#0066FF), and the public address returns the defaults.
  1. In Primary Brand Colour type red and click Save.
  2. Through the API try a logo of javascript:alert(1) and a company name of 81 characters.
ExpectedThe screen shows Primary colour must be a hex colour such as #0066FF. (clicked). The API refuses the logo (Logo must be an http(s) URL or a PNG, JPEG, GIF or WebP image.) and the long name (Company name must be 80 characters or fewer.); a logo over 500 KB is refused too. Nothing is stored.

ExpectedThe application darkens any colour whose contrast against white text is below 3:1, so #FFFF99 is shown as #97975A and white text stays readable. The saved value is unchanged; only the displayed shade is corrected. A very dark colour is handled in the dark theme: #05050F is shown as #717177 when the dark theme is switched on, and as saved in the light theme (clicked, read from the page). The workspace avatar in the sidebar uses the same corrected shade.

  2. Return to the desktop width.

Credentials and secrets

BRD §14.2 (communication and integration configuration) — masked, encrypted and kept out of logs.

  1. In a throwaway tenant, on the Configuration page, find SMTP Password (key integration.email.smtp_password). The box is a password field. Type a dummy value (never a real one) and click Save.
  2. Look at the row after saving, and open the page's text. Do the same for Telephony API Key through the API.
ExpectedAfter saving, the box shows ••••••••; the dummy value appears nowhere on the page. The settings list answers •••••••• for every credential, and the answer to the save itself no longer carries the value (not even in encrypted form). Credentials are never sent back.
  1. Needs a person with database access (read-only): read the stored configuration row, the email-sender row and the webhook row for the dummy credentials. Read the Audit Logs screen and the server log for the dummy text.
  2. Write a validation rule or flow formula that calls CONFIG("integration.email.smtp_password").
ExpectedThe stored values begin enc: followed by random text (AES-256-GCM, a fresh random value per save); the dummy text is not in the row. The audit entry records only the key name (tenant_config_update), and the server log and audit records do not contain the dummy text. Formulas receive nothing for a credential key, so a rule cannot copy a secret into a record or an error message. The key is the server's ENCRYPTION_KEY setting; the server now refuses to start in production without it. There is no automatic key rotation.
  1. Create an email sender (the Email Senders screen, or POST /api/v1/email-senders; the acceptance run used the API) with a dummy SMTP password, and a webhook with POST /api/v1/webhooks. List both through the screens or API.
  2. Needs a person with database access: read both stored rows.
ExpectedThe sender list never contains the user name or password. A webhook shows its signing secret once, at creation, and never again. Both are stored as enc:…. Sending mail and signing webhook calls still work: the model decrypts on use. Rows saved before this change are still read correctly (as plain text) and are encrypted the next time they are saved.
  1. On a throwaway tenant save WhatsApp Access Token, Meta App Secret and Telephony API Key with dummy values. A Super User may also save a platform-wide default for the same keys (test 3).
  2. Needs a person with a test channel: send a WhatsApp message and post a signed inbound telephony call to a channel account that has no credential of its own.
ExpectedThe WhatsApp request carries the channel account's own token if it has one, else the company's, else the platform's, else the message stays queued with Missing accessToken. An inbound call or Meta message is accepted only if it is signed with the account's secret, else the company's key, else the platform's; a different company's key is refused (401). Proved by the suite with the HTTP call to the provider stubbed (no message is sent); not clicked.
  1. Needs a person with a mail catcher: start any local SMTP catcher on the machine (for example MailHog, or python3 -m aiosmtpd -n -l 127.0.0.1:1025). Create an email sender on a throwaway tenant: host 127.0.0.1, port 1025, a dummy user and a dummy password.
  2. Click the sender's Send test email (or POST /api/v1/email-senders/<id>/test with a to address).
ExpectedThe catcher receives one message and shows the dummy user and password in its sign-in step: the application decrypts the stored password to use it. The answers to the create, test and list calls, and the application log, never contain the password. Proved by the suite with its own capture server (nothing left the machine).
  1. Needs a person with a local receiver: run any local HTTP receiver that prints the X-Webhook-Signature header and the raw body. Create a webhook pointing at it (POST /api/v1/webhooks) and keep the secret from the answer: it is shown once.
  2. Call POST /api/v1/webhooks/<id>/test. For a retry, record a failed delivery log row that is due, or let a real failed delivery be retried.
ExpectedThe receiver gets sha256= plus the HMAC-SHA256 of the body computed with the secret you saved, both for the test and for the retry (recomputed in the suite and compared). The delivery log and the webhook list never show the secret. A secret or company id supplied by the caller in the create call is ignored; before this change a caller-supplied secret was stored while a different one was shown.
  1. With dummy credentials saved (the credentials tests above), search for the word integration, open Audit Logs and read the change entries, and read the Configuration, Channel Accounts, Email Senders and Webhooks lists.
  2. Write a validation rule or a flow formula that reads a credential with CONFIG("integration.meta.app_secret").
ExpectedNo screen or answer contains a dummy value. The change history records only that a key changed, never its value. Credentials are not held in any record object, so the report builder, dashboard widgets, Data Export and search (which read records only) cannot reach them; flows and approvals receive nothing for a credential key, so it cannot be copied into a record, an error message or a flow's history. Proved by the suite, which searches every answer, the audit records, the stored rows and the application log for random dummy text. A custom field a company creates to hold a secret is an ordinary field and is exported and reported like any other.

Known limits

Worth knowing

  • Settings now acted on: default currency, call-recording retention (0 = keep), communication consent, default communication template, and the WhatsApp, Meta, telephony and webhook keys. Still not built: the Meta Messenger/Instagram page token and each channel account's own provider credentials keep living on the channel account (encrypted), because they are per page or number, not per company; call recordings themselves are not stored by Salesdam, only their link, so retention removes the link; no setting yet drives the language or time zone.
  • The Configuration screen cannot edit an existing platform-wide default (only add a new one); that is done through the API, by a Super User.
  • Logos are uploaded as a small image (up to 500 KB) or linked by address. The login page needs to know the tenant: it uses ?tenant= in the address or the tenant last used in that browser; an address without either shows Salesdam.
  • The browser tab title on application pages and the workspace name in the sidebar are not branded; the company name appears in the top bar when no logo is set.
  • Encryption key. Credentials are encrypted with the server's ENCRYPTION_KEY setting (documented in .env.example). In production the server refuses to start without it; set it to a long random value (node -e "console.log(require('crypto').randomBytes(32).toString('hex'))") in the server's environment, and keep a copy: without the key stored credentials cannot be read. To change the key, run node scripts/rotateEncryptionKey.mjs with OLD_ENCRYPTION_KEY and the new ENCRYPTION_KEY set (a dry run first, then --apply); it re-encrypts configuration secrets, email-sender passwords, webhook secrets, channel-account credentials and MFA secrets. The re-encryption helper is covered by a suite check; the full script was not run against live data.
  • The deployment package (Section 13) deliberately omits credentials.
