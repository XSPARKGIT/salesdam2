The seven rules on Policy

  • Funeral Plan needs a policy document link — blocks when Type is Funeral Plan and Policy Document URL is blank. Message shown on Policy Document URL.
  • Policy number is locked once saved — ISCHANGED(policy_number). Shown on Policy Number.
  • Monthly premium must be above zero and Start date cannot be in the future — two rules that can fail together. Each shown on its own field.
  • Credit Life premium is capped — Type is Credit Life and premium above R10 000. Shown at the top of the record.
  • Province must be Gauteng (switched off) — inactive; it must never block anything.
  • Premium below this company minimum — reads the company setting deals.minimum_value (currently 0, i.e. no minimum).

Existing records: POL-00001, POL-00003 (Credit Life) and POL-00004 (Funeral Plan, with a document link) all satisfy these rules.

Things worth knowing before you begin

  • Pages take a while to open. The application runs on your machine but its database is in the cloud, so a screen can take ten to thirty seconds to fill in. Give a page time before deciding it is stuck.
  • Write the formula with == for equals (type == "Funeral Plan"); a single = is refused with a message that says so.
  • Tests that create something delete it again. The test records are VR-MAN-1 and VR-MAN-2 (and VR-IMP-1 if you run the import); Test 18 is the final tidy-up. Tests 3 and 14 change a rule and a company setting and put them back.
  • Where a field is already marked required on the screen (for example Broker Email on the Policy form) that comes from the page layout, and is reported before any validation rule is looked at.

Part 1 — Writing a rule

BRD §6.1. Rules live on the object under Setup → Objects → [object] → Validations.

  1. Go to Setup → Objects and open Policy, then the Validations tab.
  2. Read the tab title and the summary line under the Add Rule button.
  3. Go back, open Insured Life and look at its Validations tab.
Expected Policy shows Validations (7) and the line 6 of 7 rules enforced on save · 1 inactive — seven rules on one object. Insured Life shows Validations (0) and No validation rules yet: rules belong to the object they were written on.
  1. On Policy → Validations, find Funeral Plan needs a policy document link.
  2. Read its card: name, Active badge, description, BLOCKS SAVE WHEN and MESSAGE.
  3. Click the pencil (Edit rule). Look at every control in the dialog, then click Cancel.
Expected The card shows the formula type == "Funeral Plan" AND ISBLANK(policy_document_url) and the message Add the policy document link for a Funeral Plan. The dialog offers Rule Name, Description, an Active switch, the formula box with its Error Message, and Error Location with two choices: Top of record or Specific field (here Policy Document URL).
  1. On Policy → Validations click Add Rule.
  2. Rule Name: Claims lodged is capped. Description: Section 6 test rule.
  3. In the formula box type claims_lodged > 20. In Error Message type No more than 20 claims can be lodged.
  4. Under Error Location choose Specific field and pick Claims Lodged. Leave Active ticked.
  5. Click Add Rule.
Expected The dialog closes and the list now reads Validations (8) and 7 of 8 rules enforced on save. The new rule shows Active. Changes on this tab save immediately — there is no separate Save step.
Note The rule is removed again in Test 17.
  1. On the Validations tab find Province must be Gauteng (switched off) — it shows Inactive.
  2. Click its toggle (Not enforced — click to start enforcing). The summary line changes. Click the toggle again to switch it off.
  3. Go to Policies → New Policy. Fill in: Type Life Cover, Province Western Cape, Broker Email manual@example.com, Monthly Premium 800, Start Date 1 January 2026, Policy Number VR-MAN-1. Click Create Record.
Expected Switching the rule on makes the summary read 8 of 8 rules enforced on save; switching it off returns it to 7 of 8 … · 1 inactive. With the Gauteng rule off, the Western Cape policy saves — the same rule, if it were on, would refuse any province but Gauteng. The new record opens.

  1. On the Validations tab click Add Rule. Click Fields, then Functions, then Examples; in Functions click ISBLANK.
  2. Clear the formula box. Type monthy_premium < 5 and wait a few seconds.
  3. Replace it with monthly_premium + 1, then with monthly_premium <, then with monthly_premium < 5.

  1. In a rule dialog, open Functions and note which of these are listed: IF, LENGTH, YEAR, TODAY, CONTAINS, REGEX, ISBLANK, AND, OR, NOT, ISCHANGED, CONFIG. Cancel.

Still to be covered

These points sit outside this script:

  • Flows, incoming webhooks, record merge and scripts. Writes that do not come from a screen are held to the same rules — a blocked flow step is recorded as a Flow Error, a blocked webhook returns every message, and the same applies to the custom-code createRecord/updateRecord helpers. They need a flow, a webhook caller or a script to drive them, so they are proven by the platform's automated checks: rules and tenant thresholds on update, import, flow step and webhook (18 checks); rule behaviour including ISCHANGED, inline edit and toggling (22 checks); rule changes written to the audit log (29 checks).
  • System-driven insurance workflows. The Insurance module moves policies through their lifecycle (for example status changes at billing and reinstatement) with its own internal writes. Those writes are not run through an object's validation rules, so a rule cannot stop the platform itself from moving a policy to Lapsed.
  • Administrator import with validation bypass. An administrator can tick bypass validation for a one-off import; rules are then skipped by design. A normal import always enforces them.
  • Layout-only rules. A field a page layout marks Required (or Read-only) is enforced on the screen, not by the API; validation rules are enforced everywhere.
  • Existing records that no longer pass. A new or tightened rule is not applied to records already saved; such a record is simply refused the next time anyone edits it, until it is corrected.

Reporting a problem

For anything that does not match the expected result, note the test number, what you saw instead, and the record you were working on. A screenshot of the screen as it looked when it went wrong is usually enough for us to reproduce it.
