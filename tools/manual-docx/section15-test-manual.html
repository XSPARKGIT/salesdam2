Custom Code and Extensibility

A step-by-step script for BRD Section 15. You create tenant code, move it Draft → Test → Active → Inactive, test-run it safely, call it from a Flow, see it read and write records and return values, watch the runtime contain loops, crashes and escape attempts, and generate documents from templates by hand and from a Flow.

Signing in

Address

What is prepared on My Company

  • Custom code s15_claim_review (reads, queries, creates and updates claims, returns a risk value) and s15_always_fails (always raises an error), both Active.
  • Flow S15 Code Flow (Claim created and claim number is S15-CODE) and flow S15 PDF Flow (claim number is S15-PDF), both Active. Other claims are not touched.
  • PDF templates S15 Claim Letter and S15 Policy Schedule.
  • Run the code-runtime tests (Tests 1–7 and 14–19) in a copy of your tenant, not in production: Setup → Deployments → Clone Sandbox Tenant, name it S15 Sandbox, switch to it with the Tenant switcher. A copy has no records, so record tests (9–13, 21–23) use My Company.

Safe-testing rules

  • The security tests use probes that only report whether something is reachable. Do not paste code from other sources into a snippet, and never put real credentials into one.
  • Leave Test mode ticked unless a test says otherwise. A run that is not in test mode writes real records.

Cleaning up

  • Delete your snippets (Setup → Custom Code, trash icon) and the S15 claims (Recycle Bin). Switch back to your home tenant, then remove the copy with Setup → Deployments → Delete sandbox… (type its name).

The runtime: limits and isolation

BRD §15.4.1, §15.4.19–§15.4.30 — what the code cannot do, and what it cannot take down.

  1. Open the card for s15_demo (Edit), replace the code with while (true) {} in the draft, click Save changes, then Execute.
  2. Open any other page (for example Home).
ExpectedAfter about five seconds the panel reads Script execution timed out after 5000ms and the rest of the application keeps answering. (The same loop in a Flow fails only that step.)
  1. Replace the draft's code with function f(n) { return f(n + 1) + 1 } result = f(0); and Execute.
  2. Replace it with a script that keeps adding large arrays to a list and Execute (Needs a person: write the loop yourself; it is stopped within a second or two by a 64 MB cap).
ExpectedThe first run reports Maximum call stack size exceeded. The second reports Execution stopped (resource limit or crash). Each run is a separate short-lived process, so neither can take the server down; after both, other pages load normally. A snippet cannot be started again while it is already running (429 recursion blocked) and a tenant may run at most five at once (both by code and suite design, not exercised here); code has no way to call another snippet or start a Flow, so Flow → code → Flow loops cannot form.
  1. Execute a snippet containing throw new Error("boom").
  2. Execute one containing Promise.reject(new Error("rej")); result = "after";.
ExpectedThe first shows failed: boom. The second succeeds with output after: an unhandled rejection in tenant code cannot crash the server. The list and every other page still work.
  1. Create a snippet with the code result = (function () { var o = {}; try { o.escape = typeof inputs.constructor.constructor('return 1')(); } catch (e) { o.escape = 'refused'; } o.process = typeof process; o.require = typeof require; return o; })();, mark it Test and Execute it.
ExpectedThe output is escape: refused, process: undefined, require: undefined. Running code from a string is switched off, there is no process, require or file access, and the script runs in its own operating-system process that has no file-system, child-process or worker permission and an empty environment. Residual limit: see Known limits (the run still has a network).
  1. Execute callApi("Not Approved", "/x").then(function () { result = "called"; }, function (e) { result = "refused: " + e.message; }); in Test mode.
  2. Needs a person: add the system under External Objects (base address and credential), then call callApi("<its name>", "/path").
ExpectedThe unapproved name is refused with is not an approved external system for this tenant. For an approved system the call goes only to its host (a full URL or a different host is refused), the credential is attached by the server and is never visible to the code, test runs are limited to GET, and the reply is capped at 1 MB. The approved path was proved by code and suite, not clicked.
  1. Execute createRecord("claim", { description: "x" }).then(function () { result = "wrote"; }, function (e) { result = e.message; }); with Test mode ticked.
ExpectedThe result is Test mode: createRecord is disabled to prevent production changes. and no claim appears. Known limits

Worth knowing

  • How the code is isolated. Each run starts its own operating-system process (Node permission model: no files, no child processes, no workers, no add-ons; empty environment; 64 MB heap; text-to-code switched off) and every data call goes back to the server, which fixes the tenant. This is much stronger than a plain Node vm context, which is not a security boundary and was what the platform used before this section; it is still not a hardware-isolated sandbox. Residual risks: the run process can still open network connections (including to internal addresses) because the Node permission model does not restrict the network, and a flaw in Node itself would be an escape; a container or separate host for the runner would close both and is the recommended next step before untrusted developers are allowed to write code.
  • Code runs with the platform's authority, not the triggering user's. It is limited to the tenant, but it does not apply the user's role, sharing or field security, so only people trusted with Deploy Custom Code should activate code.
  • Display gaps. The code card does not show tenant, created by/date, last modified by/date or an API name (the data is stored); the version tags show Draft, Test, Active, Inactive and Archived.
  • Not built: custom screens written in code, code attached directly to an object event or button without a Flow, tenant-defined REST endpoints (an inbound webhook can name a snippet to run), electronic signature capture, per-user permission checks inside documents, document-template UI for related-record tables and the logo block (set in the template data).
  • Existing mechanisms for §15.2: custom actions and buttons — action buttons that start a Flow or Screen Flow; custom screens — Screen Flows; custom integrations — Webhooks, Integrations and External Objects, the HTTP Request step and callApi; custom calculations — formula and roll-up fields and code; custom processes — Flows and Approvals; custom APIs — inbound webhooks; custom documents — PDF templates; functionality on any object — Flows with a Custom Code step.
