Permissions and Sharing

A step-by-step script for testing BRD Section 9. You are checking that Profiles control which objects and fields a person can use, that records are shared only as the organisation-wide default, the manager chain and sharing rules allow, that each administrative capability is a separate permission enforced on the server, and that the Apps a person sees follow their Profile.

Before you start

Sign in as the administrator, then confirm the test profiles and people below are in place. Most tests need a second person signed in at the same time as a test user — use a private (incognito) browser window for each, so you stay signed in as the administrator in the main window.

Things worth knowing before you begin

  • Pages take a while to open. The application runs on your machine but its database is in the cloud, so a screen can take ten to thirty seconds to fill in.
  • Tests that change a setting put it back: the organisation-wide default is returned to Private, the sharing rule is deleted, and Carol's profile is cleared (Test 38).
  • Administrators see everything. Administrator and Super User bypass the record, field and system-permission checks by design, so a person holding one of those profiles will always see the full result. Use the test people for the "refused" results.
  • A record you may not see looks like it does not exist. Opening a colleague's private case by its address shows "not found" rather than "forbidden" — that is deliberate.
  • Earlier fixtures (POL-00001, POL-00003, POL-00004, the Claim records) are not touched by this script.

Still to be covered

These points sit outside this script:

  • Screens as the test people. The browser pane used for the automated run could not sign in as a second person without signing the administrator out, so on-screen behaviour as Amahle, Refilwe, Carol and the others is described from the interface responses, not clicked. A person must confirm it with private windows (the tests that need this are marked).
  • Call recordings. A recording link is created by a telephony provider; it cannot be entered on screen. Proven through the interface calls only.
  • Delete confirmations. Deleting a role or a sharing rule asks the browser to confirm, which an automated run cannot accept; the deletions were done through the interface calls.
  • Webhooks, Analytics. Manage Webhooks, View Analytics and Manage Analytics exist as additional system permissions beyond the BRD's list. The first is enforced on every webhook route; the Analytics pair is stored and used by the screens, not checked here.
  • Hierarchy depth. The manager chain was tested one level deep. Multi-level visibility is proven by suite sharing-model.
  • Layout-level and API-field rules. Field security applies to forms, detail pages, lists, export, search and the record API. Internal platform writers (for example the Insurance module) do not apply field security.

Reporting a problem

For anything that does not match the expected result, note the test number, which test person you were signed in as, what you saw instead, and the record you were working on. A screenshot of the screen as it looked when it went wrong is usually enough for us to reproduce it.
