Integration Framework and API

A step-by-step script for BRD Section 17. You create and rotate API keys, call the API with them, prove that another tenant, a wrong key or a missing key is refused and logged, watch the rate limit and usage figures, send incoming webhooks, configure outgoing webhooks to a receiver of your own, see signed deliveries, retries and alerts, and read the Integration Log.

Before you start

Signing in

Address
http://localhost:5173
Who
An administrator who may manage API keys, integrations and webhooks

Ask your Salesdam contact for the sign-in details. Pages can take 10–30 seconds to fill because the database is remote. The Integrations sidebar item is shown when the feature switch VITE_FEATURE_INTEGRATIONS is true for the web application.

What you need

  • A copy of your tenant. Run the key, rate-limit and webhook tests in a copy, not in production: Setup → Deployments → Clone Sandbox Tenant, name it S17 Sandbox, switch to it with the Tenant switcher. A copy has no records, so record tests use My Company (Tests 3, 5 and 18).
  • An API client (curl, Postman, a script) for the steps marked Needs an API client. Use only your own throwaway keys; a key is shown once in the screen and must not be pasted into chats, tickets or this manual.
  • A request receiver you run yourself (any small local program that accepts HTTP posts and prints them). Never point a test at a real external system.

Safe-testing rules

  • Rate-limit tests use a throwaway key with a low limit in a copy of the tenant. Do not hammer the sign-in page or any public address.
  • Use dummy secrets only. Never put real credentials into a webhook, header or configuration value while testing.

Cleaning up

  • Delete or revoke your test keys and delete your test webhooks. Remove the Policy record S17-HOOK-1 (Recycle Bin). Switch back to your home tenant, then remove the copy with Setup → Deployments → Delete sandbox… (type its name).

Known limits

Worth knowing

  • Not built: OAuth (authorization-code or client-credentials). API keys and Bearer access tokens are the supported credentials; there is no other approved mechanism type.
  • Authentication of incoming webhooks is the API key or access token (always) plus an optional tenant HMAC secret. A per-webhook signing secret for senders, replay windows and IP allow-lists per webhook are not built (a key can have an IP list).
  • Rate limiting is per key, in memory in each server process; with several servers each applies its own count. There is also the platform-wide per-address limit. There is no per-tenant quota or billing meter.
  • Webhook payloads carry the record's fields selected by your mapping (or all fields if you leave it blank) and are not filtered by field security; map only fields the receiver may see.
  • Tokens created before this release were stored in readable form; regenerate them in Setup → Admin Settings → Integrations (new tokens are stored only as a hash).
  • Approval completed, communication sent and lead received are wired to the same dispatcher but were not exercised end to end in this acceptance (Test 20). The Admin Settings → Integrations screen (access tokens) was not clicked.
  • The Integration Log has no date filter or export, and a call refused by the rate limit appears under Authentication Failures rather than usage.
